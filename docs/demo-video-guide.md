基本功能的调用方法、导入名称和演示命令不变。查找、捕获、替换、分割、中文和多规则分类可以继续按原有方式演示。

## 一、录制前准备（不必全部录进去）

### 准备 1：进入项目根目录

本机目录：

```bash
cd /Users/jalonyan/Desktop/regex4cj
```

这里应能看到 `README.md`、`port`、`examples`、`scripts`、`tests` 等目录。后续命令除明确说明外，都在这里执行。

**目的：** 避免在错误目录下执行命令。录制期间无需解释本机其他目录。

### 准备 2：设置环境并核对版本

如果当前终端尚未设置 SDK，请把下面路径替换为实际安装目录；已配置时无需重复输入。

```bash
export CANGJIE_HOME="/实际安装位置/cangjie-1.1.3"
bash -c 'source scripts/env.sh; cjc --version; cjpm --version'
python3 --version
```

确认编译器显示 `Cangjie Compiler: 1.1.3 (cjnative)`。`CANGJIE_HOME` 指向 SDK 根目录，不是 `bin` 目录。换终端后须重新确认环境变量。

演示基本功能只需要仓颉工具链和 Python。完整 Rust 对照还需要可运行的 `cargo`、`rustc`；代码覆盖测量还需要 SDK 的 `cjcov`。

**目的：** 证明使用要求的编译器版本；安装细节可以留在录制之外。

### 准备 3：预先构建和排练

```bash
bash scripts/run.sh build
bash scripts/run.sh example
bash scripts/run.sh demo
```

检查示例正常结束，自动演示显示 `场景验收：13/13 通过` 和 `多规则分类验收：7/7 通过`。

公开命令会自动做构建检查，终端出现 `cjpm build success` 属于正常现象。预先构建可以减少录制中首次编译的等待。

**目的：** 排除环境问题，并熟悉输出出现的位置。

### 准备 4：准备完整验证结果

如果只是展示当前已归档结果，可以直接使用 `docs/validation/` 中的报告，并在讲解时说明这是录制前的验收结果。

如果要重新取得一次完整测试和覆盖率结果，运行：

```bash
bash scripts/run.sh coverage
```

它包含完整验收，不必紧接着再跑一遍 `verify`。命令可能超过十分钟；等待时可在另一终端查看：

```bash
tail -f .build/coverage/latest.log
```

观察日志的终端按 Ctrl+C 只会停止 `tail`，不要在正在运行覆盖率命令的终端中断任务。

成功应看到：

```text
Coverage acceptance passed: ...
Public entries: ...
Report: ...
```

最新结果在 `.build/coverage/latest.json`。命令失败时应查看日志解决问题，不能拿旧的通过报告代替这次结果。

如果只需要完整正确性对照而不测覆盖率：

```bash
bash scripts/run.sh verify
```

成功标志是 `Complete acceptance passed`，结果在 `.build/work/verification-run.json`。

**目的：** 为视频中的可靠性说明准备真实证据。录制前运行的结果应明确称作“此前完整验收”；如果录制本次长任务，可保留启动和结束画面，中间加速或注明等待时间。

### 准备 5：布置画面

- 建议一个代码编辑器窗口、一个终端窗口，字号足够看清中文和代码。
- 编辑器预先打开：`README.md`、`examples/consumer/src/main.cj`、`examples/consumer/cjpm.toml`、`tests/functional/search/cases.json`、`docs/test-coverage.md`。
- 终端宽度至少能完整显示一条命令；长命令可按下文使用反斜线换行。
- 每个功能只停留在“输入是什么、结果是什么、证明了什么”上，不逐行讲编译日志。
- 拍摄时主要使用项目名称、功能名称和结果，不介绍临时缓存目录、开发阶段编号等背景信息。

## 二、正式演示：按顺序操作

### 步骤 1：介绍项目（约 15 秒）

**画面：** README 顶部，突出项目名称和一句话用途。

**建议讲解：**

> regex4cj 是一个仓颉原生正则表达式库。给它一条文本规则和一段内容，就可以查找、提取、替换和分类文本。下面用订单信息展示它的实际作用。

**在演示什么：** 先让没有正则基础的观众理解库的用途。

不要将项目称作完整复刻整个 Rust regex 仓库。匹配计算由仓颉实现，Rust 用于测试对照。

### 步骤 2：确认编译器（约 10 秒）

```bash
bash -c 'source scripts/env.sh; cjc --version'
```

**预期：** 显示仓颉 `1.1.3`。

**建议讲解：**

> 当前演示使用仓颉 1.1.3 编译和运行。

**在演示什么：** 运行环境与版本适配。

### 步骤 3：查找订单号（约 30 秒，重点）

```bash
bash scripts/run.sh find '[A-Z]{2}-[0-9]{3}' 'AB-123 xx CD-456'
```

**预期匹配输出：**

```text
0       6       AB-123
10      16      CD-456
```

**操作要点：** 先用鼠标指出规则，再指出输入，最后指出两条结果。

**建议讲解：**

> 这条规则表示两个大写字母、一个短横线和三个数字。输入里有两个符合规则的订单号，库找到了它们，并给出在原文中的位置。

**在演示什么：** `Regex` 从文本中查找全部匹配，不需要应用程序手写逐字符判断。

这里演示的是“从文本中提取符合格式的片段”，不是校验整段文本只能是一个订单号。位置从 0 开始，结束位置不包含在匹配内。

### 步骤 4：现场改变输入（约 15 秒，重点）

把第二个编号少写一位：

```bash
bash scripts/run.sh find '[A-Z]{2}-[0-9]{3}' 'AB-123 xx CD-45'
```

**预期：** 只剩 `AB-123` 一条匹配。

**建议讲解：**

> 规则不变，把第二个编号缩成两位数字，它就不再匹配。结果由当前输入实时计算。

**在演示什么：** 有效与无效候选会得到不同结果，展示真实的规则判断。

可选再补一个完全不匹配的输入：

```bash
bash scripts/run.sh is-match '[A-Z]{2}-[0-9]{3}' '普通咨询'
```

输出 `false`。使用 `is-match` 能让观众清楚看到未命中，不必解释空白输出。

### 步骤 5：把订单号拆成字段（约 20 秒）

```bash
bash scripts/run.sh captures \
  '(?<prefix>[A-Z]{2})-(?<number>[0-9]{3})' \
  'AB-123'
```

**重点输出：**

```text
prefix：[0, 2) "AB"
number：[3, 6) "123"
```

实际输出还包含整体匹配和编号分组；只需用鼠标指出以上两个命名字段。

**建议讲解：**

> 找到订单号以后，还可以分别提取前缀和数字，供后续程序使用。

**在演示什么：** 命名捕获组，把匹配结果转成有意义的字段。

### 步骤 6：订单编号脱敏（约 20 秒）

```bash
bash scripts/run.sh replace-all \
  '(?<prefix>[A-Z]{2})-[0-9]{3}' \
  'AB-123 CD-456' \
  '${prefix}-***'
```

**预期：**

```text
"AB-*** CD-***"
```

**建议讲解：**

> 替换时可以保留提取出的前缀，只隐藏数字，而且一次处理所有匹配。

**在演示什么：** 批量替换和捕获字段引用，可用于格式调整或日志脱敏。

必须保留模板外面的单引号，避免终端提前处理 `${prefix}`。输出外层双引号是显示脚本用来标明字符串边界的格式。

### 步骤 7：分割字段（约 10～15 秒，可压缩）

```bash
bash scripts/run.sh split '[,;]\s*' 'a, b;c'
```

**预期：**

```text
"a"
"b"
"c"
```

**建议讲解：**

> 分隔符也可以是一条规则，这里同时处理逗号、分号以及后面的空白。

**在演示什么：** 基于规则的文本分割。

### 步骤 8：中文与 Unicode（约 15 秒）

```bash
bash scripts/run.sh find '\p{Han}+' 'A中文α'
```

**预期：**

```text
1       7       中文
```

**建议讲解：**

> 规则也可以直接表达汉字类别。这里找出“中文”，位置使用 UTF-8 字节偏移，所以两个汉字占六个字节。

**在演示什么：** Unicode 字符属性与位置计算。无需展开 Unicode 数据表实现。

### 步骤 9：多规则分类（约 25 秒，重点）

可先打开 `examples/classification-rules.json`，只展示四条“标签—规则”配置。

```bash
bash scripts/run.sh classify '订单 AB-123 需要退款'
```

**预期：**

```text
命中编号：[0, 2]
分类标签：["退款相关", "包含订单号"]
```

现场增加“发票”：

```bash
bash scripts/run.sh classify '订单 AB-123 需要退款并开具发票'
```

**预期：**

```text
命中编号：[0, 1, 2]
分类标签：["退款相关", "发票相关", "包含订单号"]
```

**建议讲解：**

> 一段文本可以同时命中多条规则。加入“发票”后，分类结果会多出一项，适合用来筛选订单或整理日志。

**在演示什么：** `RegexSet` 返回所有命中的规则编号，应用层再映射成可读标签。分类是规则匹配，不是大模型理解语义。

### 步骤 10：展示真正的仓颉调用代码（约 30 秒，重点）

**画面 A：** `examples/consumer/cjpm.toml` 中的依赖：

```toml
[dependencies]
regex4cj = { path = "../../port" }
```

**画面 B：** `examples/consumer/src/main.cj` 中的核心代码：

```cangjie
import regex4cj.*

// main 内：
let text = "order=AB-123; order=CD-456"
let orders = Regex("(?<prefix>[A-Z]{2})-(?<number>[0-9]{3})")
for (m in orders.findAll(text)) {
    println("  ${m.text} [${m.start}, ${m.end})")
}
```

这里只展示文件里的片段，不必把片段当成完整程序重新创建文件。

执行：

```bash
bash scripts/run.sh example
```

**预期：** 示例依次输出查找订单、提取编号、脱敏、分割、中文、转义和多规则分类的结果。

**建议讲解：**

> 刚才用命令行方便观察结果。应用程序实际使用时，只需要添加依赖，导入 regex4cj，再创建规则调用方法。这是仓颉程序直接使用库的示例。

**在演示什么：** 证明项目可以作为库被其他仓颉程序引用，而不只是一个终端演示脚本。Python 辅助脚本负责展示格式，匹配计算仍在仓颉实现中完成。

### 步骤 11：非法输入如何处理（约 10～15 秒，可选）

```bash
bash scripts/run.sh find '(' 'abc'
printf '退出码：%s\n' "$?"
```

**预期：** 输出 `regex parse error`、`unclosed group`，退出码为 `2`。第二条命令必须紧接第一条执行，才能读取刚才的退出码。

**建议讲解：**

> 规则本身写错时，库会指出错误，而不会默默返回一个看似正常的匹配结果。

**在演示什么：** 非法语法的错误处理。此处故意使用未闭合分组，不用它说明“我们比原仓库少支持某项功能”。

### 步骤 12：解释测试怎样组织（约 20 秒，重点）

**画面：** 编辑器打开 `tests/functional/search/cases.json`，展示一个案例的 `feature`、`pattern`、`text`、`expected_stdout`。

也可打开 `docs/testing.md` 的“查找文本”部分，展示正常输入、首次匹配、未命中、起点等条目。

**建议讲解：**

> 测试按功能组织。对每个功能，我们分别检查正常输入、没有结果、边界条件和非法参数。每条具名案例都写明输入和预期，同时与固定版本的 Rust 原仓库实现对照。

**在演示什么：** 测试不是只跑一个成功示例，而是检查一个功能在不同条件下应有的行为。

不用再介绍“第几个开发阶段”。Python 对照测试位于 `tests/`，直接调用库的仓颉原生测试位于消费者包的 `examples/consumer/src/`。

**预期末尾：**

**建议讲解：**

> 这里现场运行的是仓颉原生测试，77 项全部通过。它直接检查库的返回值、异常和状态复用等行为。

**在演示什么：** 可重复执行的原生测试，而不仅是展示预先写好的结果。

### 步骤 14：展示完整对照与覆盖率证据（约 25 秒，重点）

**最易读画面：** 打开 `docs/test-coverage.md` 的“本次实测结果”。该页面展示已归档的本轮验收结果。

**建议讲解：**

> 此外，录制前的完整验收中，47 个批量套件、91 个具名案例均通过。451 个公开可调用声明都执行到了，库代码可执行行覆盖率是 93.25%。这些是当前实现的测试证据，不表示已经移植了原仓库的 93.25%。

**在演示什么：** 大范围对照、公开入口执行情况以及实测代码覆盖率。

想在终端展示机器可读的归档证据，可以运行：

```bash
python3 - <<'PY'

assert run['run_id'] == cases['run_id'] == coverage['run_id']

print('验收状态：', run['status'])
print('具名案例通过：', sum(c['status'] == 'passed' for c in cases['cases']), '/', len(cases['cases']))
print('公开声明执行：', coverage['public_hit'], '/', coverage['public_entries'])
```

如果准备阶段重新运行了 `coverage`，优先展示那次 `.build/coverage/latest.json` 的实测结果；它不会自动改写 `docs/validation/` 的归档。不要把两次运行的数字或运行编号混用。

短视频里不必再次等待十多分钟完成全套运行。要展示启动过程，可以单独录制 `bash scripts/run.sh coverage`，然后加速到完成画面；画面上标注“中间等待已加速”。

### 扩展 C：面向技术评委罗列扩展能力

打开 `docs/status.md` 的功能表，简要指向：

- BytesRegex / BytesRegexSet：字节输入与多规则匹配。
- AST / HIR：部分语法结构的解析、转换、属性和遍历能力。
- ThompsonNfa / PikeVM、有界回溯、反向搜索：不同搜索入口和配置。
- 密集、稀疏、惰性 DFA：对应搜索、缓存和限制接口。
- 字面量提取、UTF-8 范围工具。

**建议讲解：**

> 除常用文本接口外，还提供这些面向高级使用者的扩展能力，具体支持范围和差异在文档中列明。

**在演示什么：** 告诉技术评委还有哪些实现，不在短视频里模拟复杂算法。不要把 OnePass 包装入口描述成独立的 one-pass 执行引擎，也不要声称所有扩展行为已与原仓库一致。

### 扩展 D：现场修改仓颉示例

在 `examples/consumer/src/main.cj` 中，仅把第一处 `text` 改为：

```cangjie
let text = "order=AB-123; order=CD-456; order=EF-789"
```

## 五、录制时常见问题

- **没有任何匹配行：** `find` 未匹配时本来就不输出结果；需要明确展示未命中时，用 `is-match` 得到 `false`。
- **看到 1 和 7，却只匹配两个汉字：** 位置是 UTF-8 字节偏移，不是字符序号。
- **`${prefix}` 消失了：** 检查替换模板是否使用单引号。
- **输出有双引号：** 替换、分割演示将文本按 JSON 字符串展示，便于看清空串和特殊字符。
- **命令前出现构建成功信息：** 正常现象，公开命令会检查构建状态；先等命令完成再解释业务输出。
- **捕获结果有组 0：** 组 0 是完整匹配，后面才是各个捕获字段。
- **完整测试耗时较长：** 不用在主视频里保留全部等待；展示本次启动和完成，或明确展示录制前归档证据。
- **旧 PPT 或截图数字不同：** 本轮采用 77 项原生测试、91 个具名案例、47 个批量套件、15 项工具测试；覆盖率采用本次对应报告，不沿用旧图。
- **如何描述尚未覆盖的部分：** 公开入口都执行到不等于所有条件分支已测完；当前仍有未执行行，也不等于已完成整个原仓库的全部移植。
