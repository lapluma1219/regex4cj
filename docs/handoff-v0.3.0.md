## 1. 先理解用户的真实目标

用户参加借助 AI 将外部库移植到仓颉的比赛，选定了 Rust 的 `rust-lang/regex`。长期理想是：在约定的 API 和配置下，对外功能与行为尽可能完整一致，改变的是实现语言。逐行复制 Rust 源码不是必要条件，匹配位置、顺序、捕获、配置和错误语义不能随意改变。

但用户已经明确要求：先形成完整、可验证、可演示、可交付的版本，即使它暂时不包含上游全部内容；让用户有机会运行、学习和理解，再完善下一版。不要再次把“必须先移植全部仓库”作为任何版本交付的前提。

用户的编程基础相对有限。沟通时要解释输入、输出、业务用途与可操作的验证方法，不能仅罗列 AST、HIR、NFA、DFA 等术语。必要时用一个例子贯穿说明。

用户也明确担心过度工作：此前 Unicode 能力被拆得较细，测试数量增长容易让人误以为整体接近完成。以后按“完整能力”合并推进，以验收条件结束，不用阶段编号或测试数量暗示完成百分比。

## 5. 下一较大版本的建议目标

建议暂定为：**v0.3.0 字符串 Regex / RegexSet 兼容增强与稳定交付版**。

这是一个比 v0.2.0 明显更大的里程碑，可包含多次内部提交和多个中间验收点，但最终应一次性交付完整使用流程，而不是每补一小类语法就让用户决定是否继续。

### 5.1 最终用户应该能完成的流程

1. 用 Builder 配置匹配选项，例如大小写不敏感、多行和 CRLF。
2. 构造单模式 Regex 或多规则 RegexSet。
3. 在原始文本中从指定字节位置继续搜索，并保留锚点和词边界上下文。
4. 逐条消费匹配、捕获或分割结果，而不是所有结果先生成一个大数组。
5. 复用捕获结果工作区，进行重复处理。
6. 在国际化文本和混合换行的日志上查找、分类、提取字段并替换。
7. 通过文档判断一个 API 是否对应上游、有哪些适配差异、哪些配置暂不支持。
8. 在交付包中运行演示、测试和基准，并可定位失败反例。

### 5.2 本版主要范围

| 类别 | 本版目标 |

| 模式选项 | 完成 i/x/R，补齐字符串接口允许的 u/ASCII 模式语义；保留 m/s/U 的组合和作用域行为 |

### 5.3 本版明确不作为前置条件的事项

- 任意字节 `bytes::Regex` / `bytes::RegexSet`。
- 全量 AST/HIR、自动机公共类型的逐项迁移。
- DFA、lazy DFA、预过滤器、前缀共享等全部性能引擎。

## 8. 工作包 B：建立可观察和可持续的验证方式

现有套件已经很有价值，不应推翻。但是每个小用例分别启动 Rust 与仓颉进程，验证成本较高。对较大版本可以做一项有明确收益的测试基础设施改进：批量执行或持久进程验证通道。

建议：

- 保留现有 CLI 和学习入口的兼容性。
- 为测试增加批量请求协议，使同一个参照进程处理多组案例。
- 请求明确包含操作、模式/模式集合、配置、文本、起点和额外参数。
- 响应包含状态、匹配范围、捕获、集合成员或错误类别，不只比较“成功/失败”。
- 可沿用现有十六进制文本协议并增加长度/记录边界，或选可靠的结构化协议；不要为了测试给生产库引入不必要的 JSON/网络依赖。
- 保证空字符串、换行、TAB、NUL 与 emoji 可无歧义传输。若扩展到 stdin 编码传输 NUL，要保留原生测试，不把传输成功误作语义正确。
- 固定随机种子，超时有清楚的用例标识，失败写出完整可重放案例。
- 若采用持久进程，验证一次失败不会污染下一请求，缓存键包括配置和模式。

只有在批量通道与既有单次通道对照成功后，才用它替换大量测试启动。若该改进本身迟迟不能稳定，应先保留现有方式，不要让测试平台建设阻塞功能交付。

错误比较应基于明确契约。Rust panic 与仓颉 Exception、语言类型差异需要适配；不要把不同语言的完整错误字符串直接要求逐字相同，也不要把所有错误都归成同一种“失败”而掩盖差异。

## 9. 工作包 C：配置基础与大小写/空白/换行语义

### 9.1 先建立统一选项模型

现有 Expr 保存了部分标志，后续要有清楚的默认值、内联覆盖和组内作用域规则。

要求：

- Builder 默认选项、全局内联标志、局部分组启用/禁用的优先级与上游一致。
- 离开局部分组后恢复之前选项。
- Regex 与 RegexSet 使用同一套解析配置语义。
- 锚点、点号、词边界等状态携带执行所需信息，不依赖会在编译后变动的全局标志。
- 保留已发布的 `Regex(pattern)` 和 `RegexSet(patterns)` 默认调用方式。

### 9.2 大小写不敏感 i

不要对输入和模式统一调用 lower() 来实现。那会破坏字符类、Unicode 等价关系、原始位置和捕获内容。

优先参考：

```text
regex-syntax/src/unicode.rs
regex-syntax/src/unicode_tables/case_folding_simple.rs
regex-syntax/src/hir/translate.rs
```

按固定上游的 Unicode 简单大小写折叠构建等价类，并考虑 ASCII 模式下不同的规则。简单折叠不等于 Unicode 全量多字符 case folding，不要随意让单个字符匹配多个输入字符。

需要覆盖 ASCII、希腊 sigma 变体、Kelvin sign 等非 ASCII 情况，并对 ß/SS 等容易误解的例子先由上游给出参照。捕获和返回文本必须保留原输入，不是折叠后的替代文本。

字符类取反、范围、交并差与大小写的组合必须单独验证，不能假定“最后把整个字符集合扩展一下”就符合上游的处理顺序。

### 9.3 扩展空白模式 x

不能对模式字符串预先去掉所有空白和注释。这样会破坏转义、字符类、局部作用域和错误位置。

应在词法/解析阶段处理，逐项核对空白的范围、注释终止、转义空格、转义 #、字符类内行为，以及计数重复中的空白。源码位置要映射到原模式。

### 9.4 CRLF 模式 R 与行结束符

不要把 CRLF 输入先替换成 LF；这样会改变字节偏移和匹配内容。

测试 m/s/R、局部开关、CR 与 LF 单独出现、CRLF 对中间位置、结尾换行，以及 Builder 的 line_terminator 选项。该选项的 byte 参数和字符串 UTF-8 安全约束必须按上游验证，不能简单接受任意 Rune 作为同义替换。

完成条件：新选项与原有 m/s/U、Unicode 属性、分支/重复/捕获、RegexSet 组合后通过对照，旧默认行为不变。

## 10. 工作包 D：Unicode 模式、边界、名称与剩余属性

### 10.1 u 开关不是任意字节 API

关闭 Unicode 不等于允许字符串 Regex 返回非法 UTF-8 范围。上游字符串 Regex 和 bytes Regex 的接受模式不同。

先建立上游探针矩阵：合法 ASCII 简写类、词边界、非 ASCII 字面量、点号、十六进制转义、Unicode 属性，以及局部 `(?-u:...)` 和 i 的组合。区分：

1. 模式构建时被拒绝。
2. 模式合法，但只按 ASCII 字符类别解释。
3. 匹配仍须遵守字符串 UTF-8 安全要求。

现有标量执行器能否覆盖每种合法情况要用证据判断。不要为了赶进度拒绝上游合法的重要子集后声称 u 已实现，也不要为了支持 u 就立即移植整个 bytes 引擎。如果出现架构阻碍，应在最小反例上给出方案并明确影响。

### 10.2 词边界与 Unicode 捕获名称

补齐固定上游支持的 start/end、半边界等方向性断言和其别名，测试字符串起止、换行、相邻非 ASCII 字符、组合标记和 ASCII 模式。

捕获名称按固定上游 parse_capture_name 的规则实现，不要凭“看起来像标识符”判断，也不要擅自做名称正规化或大小写转换。重复名称、非法首字符、Unicode 名称查询和替换引用需要一起验证。

### 10.3 剩余 Unicode 枚举属性集中处理

参考已经存在的生成器模式，集中导入：

```text
regex-syntax/src/unicode_tables/age.rs
regex-syntax/src/unicode_tables/grapheme_cluster_break.rs
regex-syntax/src/unicode_tables/word_break.rs
regex-syntax/src/unicode_tables/sentence_break.rs
```

保留固定提交、Unicode 版本、源文件哈希、离线快照和许可证。属性值与别名来自同一固定上游。

尤其要验证 Age 查询语义：不能仅按直觉当作“字符恰好在这个版本首次出现”；应读取上游的 ages() / class() 并用跨版本字符核对。Break 属性只是一种字符集合查询，不自动意味着实现了完整词/句子/字素簇分割算法。

不要把每张表拆成一个面向用户的新里程碑。把整类能力作为一个工作包完成。

### 10.4 其他语法差异

根据 API/语法清单集中核对计数空白、堆叠量词、八进制开关和其他转义。octal 允许八进制解析时，不代表支持了反向引用。不要照搬其他正则引擎的语法。

完成条件：本版声明支持的模式语法有正例、反例和组合例；未支持项仍明确报错。

## 11. 工作包 E：起点搜索与不同搜索目的

### 11.1 起点必须保留原文上下文

计划提供 Regex 的 isMatchAt/findAt/capturesAt 和 RegexSet 的对应起点查询。

**禁止用 text[start..] 代替原文起点搜索。** 这会改变 A/z、词边界和行边界含义。固定上游的经典例子是 `\bchew\b` 对 `eschew` 从偏移 2 搜索：原文上下文不满足词边界，截取后的 `chew` 却可能匹配。

Input 应保留完整原文和完整偏移映射，搜索入口控制允许的起始位置。返回的范围仍相对完整输入。

当前内部 search 接受标量位置，公开 Rust 接口接收字节偏移，两者不能直接互用。对落在多字节字符内部的起点，必须实测固定 Rust 行为；不要自行规定全部拒绝或简单四舍五入。对越界、末尾、空输入也单独测试。

### 11.2 isMatch、find 与 shortestMatch 不能混成一个操作

现有 isMatch 通过 find 实现，可在不改变语义的前提下加入只判断存在性的提前结束路径。

shortest_match 不是 find().end 的别名。固定上游的文档还说明返回位置可能受内部引擎启发式影响；不能把某一引擎偶然返回的值当成跨实现永恒保证。

实施时：

- 先写清它保证什么、允许什么实现差异。
- 用固定上游探针记录当前行为，同时验证契约性质。
- 若选择 earliest 路径实现，明确是否与当前固定参照完全一致。
- 不因为内部允许差异就放弃其他确定字段的严格对照。

完成条件：起点搜索和普通搜索能共享正确的上下文模型；搜索目的区分不破坏最左优先、分支优先和贪婪性。

## 12. 工作包 F：惰性迭代、捕获辅助与复用工作区

### 12.1 真正的按需迭代

保留现有 findAll/capturesAll/split 等便捷数组接口，新增匹配、捕获、分割的惰性接口；旧接口可以逐步基于同一迭代内核收集结果，减少规则重复。

不能先生成完整数组，再把数组包装为“惰性迭代器”。必须在调用方请求下一项时继续搜索。迭代器需要独立持有推进位置、前一次结束位置和输入生命周期所需的引用或副本。

重点验证：

- 只取第一项后停止，不计算所有后续结果。
- 同一 Regex 创建两个迭代器交错推进，互不影响。
- 使用者保留之前返回的 Match/Captures，再推进后内容不变。
- 空匹配不会无限循环，也不会在 Unicode 字符内部错误推进。
- 非空匹配后同位置的空匹配跳过规则与上游一致。
- split 的开头/结尾空字段、splitN 的 0/1 和最后余段行为不变。
- 回调中再次使用同一个 Regex，不破坏外部状态。

Rust 生命周期和仓颉运行时不同，允许采取安全的语言适配，但应明确分配与对象持有成本。

### 12.2 捕获元数据与便捷接口

根据清单补充 asStr、Match 的范围/长度/是否为空辅助操作、Captures 的完整匹配和组遍历，以及 static_captures_len / extract 的合理仓颉对应设计。

static_captures_len 不等于 capturesLen()：分支中实际参与的捕获数是否固定，需要语义分析。extract 也不能简单把所有未参与组替换为空字符串就视作等价。Rust const generic 可用仓颉适合的接口表达，但长度检查和失败条件必须明确。

### 12.3 捕获工作区

设计对应 CaptureLocations 和 captures_read 的可复用存储。对工作区是否能跨 Regex 复用、容量不匹配、失败查询是否保留或清空旧内容，要先查上游并写测试，不凭直觉决定。

工作区优化不应让已返回的 Captures 被后续查询覆盖。避免共享可变搜索状态导致重入出错。该能力验证完成前，不宣称线程安全。

完成条件：按需推进有证据；生命周期、空匹配、捕获缺失和复用状态等边界均有原生测试，而不只通过 CLI 输出推测。

## 13. 工作包 G：Builder 与 RegexSet 集成收口

Builder 应统一此前新增语义，而不是另一套行为不一致的实现。

对固定上游 builders.rs 的字符串部分逐项核对：unicode、case_insensitive、multi_line、dot_matches_new_line、crlf、line_terminator、swap_greed、ignore_whitespace、octal、size_limit、dfa_size_limit、nest_limit 等。

分类处理：

1. **匹配语义选项**：属于本版主要目标，必须实际生效，并验证默认/设置/内联覆盖。
2. **资源控制选项**：仓颉和 Rust 内部表示不同，不能把“状态个数”谎称为同单位内存字节限制。选择诚实的对应设计，写明计算方法、适配差异和不可配置的安全上限。
3. **未实现引擎专属选项**：例如 DFA 缓存相关配置，不能提供一个看似成功但静默忽略的 setter。应明确不支持，或公开说明真正的行为；不得以接口名字齐全冒充配置语义齐全。

保留旧构造器默认行为，Builder.build 应生成独立对象；修改 Builder 不影响已构造对象。多次 build 的行为、无效配置、超限情况有测试。

RegexSet 同步覆盖 Builder 默认选项、内联局部覆盖、起点查询和结果遍历。若实现 matches_read_at 的复用缓冲区，需要验证布尔数组长度、旧结果清理和异常后的状态。空集合、重复规则、重叠命中、升序编号这些 v0.2.0 契约不能退化。

完成条件：API 清单中的每个 Builder 选项有实际状态和证据；用户不能遇到“能设置，实际上什么也没发生”的隐性缺口。

## 14. 工作包 H：集中兼容审计，而不是只增加随机数量

### 14.1 导入适用上游语料

固定上游已有 testdata，可优先检查：

```text
flags.toml
unicode.toml
no-unicode.toml
line-terminator.toml
crlf.toml
word-boundary.toml
word-boundary-special.toml
anchored.toml
substring.toml
earliest.toml
iter.toml
empty.toml
set.toml
regression.toml
```

先阅读 testdata/README.md 和测试格式，理解每项配置、范围、模式集合和预期。不要把底层 automata 专属测试当成顶层 Regex 都必须暴露的契约。

每条用例应标注：执行并通过 / 真正失败 / 本版范围外 / 因测试适配缺失暂未执行。跳过必须记录具体理由，不能用“暂不支持”吞掉本版必做项。导入必要语料时保留来源提交和许可说明，不要求把整个上游仓库放进产品包。

### 14.2 覆盖组合，而不是只覆盖单功能

至少建立以下交叉矩阵：

- i 与 Unicode/ASCII、字符类代数、局部分组。
- x 与注释、转义、字符类、计数重复。
- m/s/R 与 LF/CR/CRLF、指定起点、输入末尾。
- 起点与 Unicode 字节中间、A/z、词边界。
- 贪婪/非贪婪与分支、空匹配、惰性迭代。
- 捕获与可选分支、重复、零次重复、工作区复用。
- RegexSet 与全部配置、重复模式、重叠模式、无命中。

随机生成器只生成声明支持且经参照验证合法的模式；非法模式另有生成和错误测试。为错误修复保留最小反例，避免每次只增加一个庞大随机种子而无法解释覆盖内容。

### 14.3 错误诊断

建议建立仓颉错误分类：模式解析、未支持选项、构建资源限制、参数/索引错误等。需要区分编译错误、运行参数错误和正常未匹配。

逐步保留原模式中的字节位置与范围。CLI 仍应有稳定非零退出码，库内不要通过打印错误后返回空结果来隐藏失败。错误文案可语言化，类别、发生阶段和必要位置要有契约。

## 15. 性能与资源：先测量，再决定优化

v0.2.0 的 set-benchmark.json 记录的是整进程启动、编译、执行合计耗时，不能作为纯匹配速度比或优化成效的最终证据。

下一版至少建立分离基准：

- 冷启动与首次构建。
- 模式编译一次的成本。
- 编译后重复查询的成本。
- isMatch、find、captures、replace 和 Set 查询分别测量。
- 单规则、多个短规则、少量复杂规则、Unicode 大字符类。
- 无匹配、早命中、晚命中、大量命中和大量空匹配。
- 只消费迭代第一项与消费全部结果的时间/内存差异。

采用固定输入、固定种子、预热与多次重复，报告中位数和明确的测量范围。能可靠测量峰值内存时记录；不能测时明确写“未测”，不要用猜测填表。

保留资源保护。避免指数回溯不意味着整个 API 都是线性：重复搜索、捕获复制、结果收集和字符类操作都可能带来额外成本。不要在 README 承诺未经证明的复杂度。

优化优先级由基准决定，例如减少重复 Input 转换、避免 isMatch 构造匹配文本、复用工作区、减少捕获数组复制。没有证据时不要重构整个引擎，也不为缩短一次微基准就牺牲结果独立性或语义。

## 17. 最终交付必须包含的内容

### 17.1 稳定的运行入口

尽量保留：

```sh
bash scripts/run.sh demo
bash scripts/run.sh example
bash scripts/run.sh check
bash scripts/run.sh verify
bash scripts/run.sh classify '你的文本'
```

必要时新增命令，但避免破坏已有调用。CLI 测试协议可以有版本化扩展，用户入口要有清楚帮助。

建议新增三个完整应用演示：

1. **国际化日志查找**：使用 Builder 配置大小写、多行和 CRLF，从混合文本提取字段。
2. **按需遍历与继续搜索**：用户只取前几条匹配，再通过原文起点继续处理，解释字节位置和上下文。
3. **多规则配置分类**：同一规则集合使用配置、起点和成员结果，保持标签层与匹配层分离。

每个演示有独立预期，显示输入、配置、结果和通过/失败，包含至少一个正常无结果和一个明确错误场景。不要做成打印固定答案的展示。

### 17.2 文档与兼容报告

应交付：

- 更新后的 README、上手、API、学习指南。
- `docs/api-coverage.md`，逐项列出状态与适配差异。
- `docs/release-0.3.0.md`，明确本版范围。
- 已知限制与完整未覆盖清单。
- Unicode 数据来源、生成步骤和许可证。
- 测试命令、环境、实际退出码和可重放反例。
- 性能测量方法与结果，不把进程耗时当作吞吐。
- CHANGELOG 和统一的包版本。

不要把历史 v0.1.0/v0.2.0 的验收结果改写为新版本的结果。历史包保留，当前入口指向新版本。

### 17.3 源码包与复现

沿用 package.sh，从已提交的干净版本生成源码包和 SHA-256。包内包含构建清单、锁文件、测试、数据与文档，不依赖开发机完整上游或技能库才能正常构建。

解压到新目录，确认没有旧构建产物，重新构建并运行演示和原生测试。完整差分验收应针对最终代码执行；若解压包又改变了代码或依赖，需要补相应验证。

明确区分：

- 新源码目录验证。
- 使用已有 SDK/依赖缓存的验证。
- 全新系统/另一平台验证。

做到哪一级就报告哪一级。若测试了另一平台，记录具体 OS、架构、SDK 和工具版本；未测试的平台不要写“已支持”。

## 18. 本里程碑的 Definition of Done

只有满足以下条件，才宣告该较大版本完成：

1. A 阶段确定的本版必做项全部有实现与验证；没有把必做项偷偷移到排除清单。
2. 目标用户流程可完整运行，不需要用户拼接尚未公开的内部接口。
3. 旧公开接口和示例可用；确有破坏性变化时有明确迁移说明与用户认可的处理。
